Both candy pins dated from **day 235** while the org resolves those candies at day 239/243. A
published tag embeds the pins it carried **at mint time**, and this repo's tag is what consuming
projects fetch — so every closure pinning `pod-kde-desktop` drags the day-235 `pod-pipewire` in.
Measured in a real consuming closure (`distro-cachyos`, every in-tree ref at its newest tag,
stock `task build:binary` charly):

  using newest 2026.243.0100 (from github.com/opencharly/pod-pipewire@v2026.243.0508),

That consuming repo **cannot clear this** — the stale pin is inside this repo's published tag,

### 2. The repo's own gate was red, and this fixes it

`charly box validate` failed at this root, and the `candy` workflow has been red on `main` since
2026-08-25:

```
validation error: candy "kde-desktop" candy: unknown candy "kde-shell"
```

The manifest listed `kde-shell` as a **bare** ref while every other entry is a pinned `@github`
ref. Nothing in this repo declares that entity, and a bare name resolves only inside a consuming
project's closure — so the manifest could never validate standalone, which is precisely what its
own gate does. `kde-shell` is declared by `opencharly/layer-kde-shell`; it was simply never
pinned here.

**An earlier revision of this PR described that failure and moved on, parking it as out of scope
for this change.** That framing is banned by the rulebook and the block was correct: the gate was
red, the cause was one missing pin in the very file this PR edits, and it belongs in this change
rather than behind a follow-up. It is fixed here, in commit `f951eb7`.

## The candy's own `version:` is deliberately NOT bumped

`PickCandyVersion` (`sdk/loaderkit/candy_version.go`) warns only when two materializations of a
bare ref carry **different per-entity `version:` values**:

```go
for _, c := range cands {
    if c.Version != best.Version {   // <- entity version, not the git tag
        warn("Warning: candy %s resolved to multiple versions; …")
```

Identical entity versions across different git tags resolve silently, on tag freshness. Bumping
the stamp for a pin-only change would therefore **manufacture** the exact warning this PR
removes, for every consumer still pinning an older tag of this repo.
